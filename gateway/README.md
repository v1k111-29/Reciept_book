# gateway/ (owner: P3)

A thin HTTP bridge between the Python backend and **Drunix** (NPCI's Hyperledger Fabric
2.5-compatible blockchain). It is a Node/TypeScript service built on `@hyperledger/fabric-gateway`.
The reason it exists is in `IMPLEMENTATION_PLAN.md` Part 1.2: the Fabric Gateway client libraries
are for Go, Node and Java, and we know of no maintained Python one [I].

## What it does

- Takes a `GatewayRequest` from the backend, signs and sends it to Drunix as the org named by
  `identity`, and returns a `GatewayResult`.
- Keeps one gRPC connection and one Fabric identity per configured `OrgRole`.
- Waits for the commit status on writes, so "invalidated at commit" and "outcome unknown" are
  different answers.
- Turns Fabric and chaincode failures into an `ErrorCode` and an HTTP status.

## What it does not do

- No business rules. Who may write what, and in which order, is decided by the chaincode
  (`chaincode/src/rules.ts`). The gateway only checks the request shape.
- No hashing, no storage. The backend decides whether to retry (`RETRYABLE_ERRORS`). The one
  retry in the gateway is an endorsement whose peers' results differ, before anything is ordered
  (`MISMATCH_RETRY`, see below).
- It does not hold keys in git. Credentials are file paths in environment variables.

## HTTP routes

Routes are `GATEWAY_ROUTES` in `backend/s14/contracts.py`. Bodies are JSON.

| Route | Request | Success body |
|---|---|---|
| `GET /health` | none | `HealthResponse`: `{status: "ok", contracts_version}` |
| `POST /submit` | `GatewayRequest` | `GatewayResult`, HTTP 200, `ok: true`, `tx_id` set |
| `POST /evaluate` | `GatewayRequest` | `GatewayResult`, HTTP 200, `ok: true`, `tx_id` always `null` |

`GatewayRequest` is `{function, args, identity}`. `function` is a `ChaincodeFunction`; `args` is
an array of strings (default `[]`); `identity` is an `OrgRole`. The payload in `GatewayResult` is
the chaincode's response parsed as JSON (shape per `CHAINCODE_RESULT`), never a JSON string.

The gateway answers `VALIDATION` (422) when:
- the body is not a JSON object, is over 1 MB, or has a field other than `function`, `args`, `identity`;
- `function` or `identity` is unknown, or `args` is not strings or has the wrong count (`CHAINCODE_ARGS`);
- a write (`CHAINCODE_WRITES`) is sent to `/evaluate`, or a read to `/submit`;
- `identity` has no credentials configured (for example `CUSTOMS_VIEWER` before N3);
- the route does not exist.

With no ledger configured the gateway answers `LEDGER_UNAVAILABLE` (503).

## Error mapping

Failed responses carry `GatewayResult` with `ok: false` and the HTTP status from
`ERROR_HTTP_STATUS`. Rules are in the `GatewayResult` docstring (D-20, D-21) and `src/ledger/errors.ts`.

| Situation | ErrorCode | HTTP |
|---|---|---|
| Chaincode error, read from `chaincode response 500, <ErrorCode>: ...` in the peers' details | that code | per `ERROR_HTTP_STATUS` |
| Peers report different codes | `ENDORSEMENT_FAILED` | 502 |
| Peers' results differ ("ProposalResponsePayloads do not match") on every attempt | `INTERNAL` | 500 |
| Unknown or no code in the details | `INTERNAL` | 500 |
| Commit code `MVCC_READ_CONFLICT` | `MVCC_CONFLICT` (retryable) | 409 |
| Commit code `ENDORSEMENT_POLICY_FAILURE` | `ENDORSEMENT_FAILED` | 502 |
| Any other commit code | `INTERNAL` | 500 |
| Sent with a tx id but commit status unknown | `OUTCOME_UNKNOWN`, always with `tx_id`; never auto-retry | 504 |
| Peer or orderer not reached | `LEDGER_UNAVAILABLE` | 503 |
| Chaincode response is not JSON | `INTERNAL` (keeps `tx_id` if committed) | 500 |

## Configuration (environment variables)

Read by `src/config.ts`. For `<ROLE>` use an `OrgRole`: `AD_BANK`, `EXPORTERS_BODY`, or the
optional `CUSTOMS_VIEWER`.

| Variable | Meaning |
|---|---|
| `S14_GATEWAY_PORT` | Default `8800`. Integer 1-65535. |
| `S14_CHANNEL`, `S14_CHAINCODE` | Both default to `receiptbook`. |
| `S14_<ROLE>_MSP_ID` | For example `Org1MSP`. Must agree with `DEFAULT_MSP_ROLES`. |
| `S14_<ROLE>_PEER_ENDPOINT` | For example `localhost:7051`. |
| `S14_<ROLE>_TLS_CERT` | Path to the peer's TLS CA certificate. |
| `S14_<ROLE>_CERT`, `S14_<ROLE>_KEY` | Paths to the client certificate and private key. |
| `S14_<ROLE>_PEER_HOST_ALIAS` | Optional TLS host name override, for example `peer0.org1.example.com`. |

`AD_BANK` and `EXPORTERS_BODY` are required, with all five main variables each. `CUSTOMS_VIEWER`
is optional, but once one of its variables is set, all are needed. All missing names are reported
in one error.

The gRPC deadlines (`DEADLINES_MS` in `src/ledger/fabric.ts`) are chosen budgets, not
measurements. Endorse plus submit plus commit status stay under the 10 s timeout of p4's
`HttpGateway`, so a slow commit comes back as `OUTCOME_UNKNOWN`, not `LEDGER_UNAVAILABLE`
(REQ-p3-6). They were set on the emulated test network [I]; retune on your host.

`MISMATCH_RETRY` (same file, ISS-p3-10 in docs/logs/p3.md): when the endorsing peers read
different versions of a key (a write right after another one on the same key, committed on one
org's peer but not yet on the other's), the peer gateway answers "ProposalResponsePayloads do not
match" and nothing is ordered. The gateway then sends a new proposal (new tx id), up to 3 attempts
in total, 300 ms apart, and starts a new attempt only while at most 0.9 s has been used, so the
worst case stays at 9.9 s. Nothing else is retried: not other endorse failures, nothing after the
submit to the orderer, no commit failure, never `OUTCOME_UNKNOWN`.

After a write is VALID on the submitting org's peer, the gateway also waits until the other org's
peer has committed it (ISS-p3-11), so the next write, endorsed by both orgs, sees it on both. It
uses its connection for the other org (`Gateway.newCommit` with the submitter's signed commit
status request) and only what is left of the attempt's 9 s, so the 9.9 s worst case above still
holds. If that wait times out or fails, or the other peer reports another validation code, the
gateway logs one warning line and still returns the successful result: the transaction is valid
on the submitting org, and validation is deterministic. With only one org configured there is no
second wait.

## Build, typecheck, test

```bash
cd gateway
npm ci
npm run typecheck     # tsc --noEmit (src, NodeNext) + tsc -p tsconfig.test.json (src + test/)
npm test              # vitest run (73 tests on 24 Oct 2026)
npm run build         # tsc -> dist/
npm run dev           # tsx src/main.ts
```

## Run against the Drunix test network

The network belongs to P3; setup, ports and caveats are in `network/README.md`.

```bash
bash network/up.sh && bash network/deploy.sh      # once; see network/README.md first
source network/gateway-env.sh && (cd gateway && npm run dev)    # gateway on :8800
curl -s localhost:8800/health
```

`network/gateway-env.sh` sets the `S14_*` variables for `AD_BANK` (Org1MSP, lite peer
`localhost:7051`) and `EXPORTERS_BODY` (Org2MSP, `localhost:9051`). It sets paths only; cryptogen
keeps the file names fixed, so they survive `network/down.sh` + `up.sh` (docs/logs/p3.md,
2026-10-21 14:24). Both lite and committing peers serve the Gateway API (U-02, closed).

Live evidence in `docs/logs/p3.md`: HTTP -> validation -> Drunix -> chaincode -> error mapping
(2026-10-21 14:24, against the stub chaincode); the commit-code mapping for
`ENDORSEMENT_POLICY_FAILURE` -> 502 `ENDORSEMENT_FAILED` (2026-10-22 20:22, on Drunix's `basic`
sample). On 25 Oct 2026 the live suite (`/submit` and `/evaluate` on `receiptbook`, all five
milestones and each rejected write) and the endorsement test on `receiptbook` passed in
`.github/workflows/live.yml` (D-33), which resolves DEP-p3-2 and DEP-p3-3.

## Known issues

- ISS-p3-9: if the host sleeps, YugabyteDB can die inside its container and the committing peer
  then panics. After any sleep, run the health check in `network/README.md` before testing or
  demoing; rebuild if it fails.
- ISS-p3-8: TypeScript chaincode needs the `fabric-nodeenv` image workaround on every machine that
  deploys it (see `chaincode/README.md`).
- `npm audit` reports vulnerabilities in dev-only test tooling (vitest 3.2.7 dependencies,
  ISS-p3-3). The fix is a breaking major upgrade; the decision is the lead's (D-24).
- `peer chaincode invoke --waitForEvent` times out against lite peers; use
  `bash network/last-block.sh <1|2>` to see the newest block and validation codes.
