# chaincode/ (owner: P2)

The `receiptbook` smart contract for S14 Receipt Book. It runs on **Drunix** (NPCI's
Hyperledger Fabric 2.5-compatible blockchain), written in TypeScript. The wider design is in
`IMPLEMENTATION_PLAN.md` Part 1.2; the problem is in `docs/PROBLEM.md`.

## What it does

- Keeps one record per shipping bill. The key is `sb_hash` (a salted hash, never the raw
  shipping-bill number). The value is a `ShippingBillRecord` as JSON, with its list of events.
- Accepts a milestone only if the rules allow it: who may write it, whether it is a duplicate,
  and whether the earlier milestones are already on the record.
- Stamps each event with `tx_id`, `ledger_time`, `submitter_msp` and `submitter_role`.
- Emits the chaincode event `MilestoneRecorded` (payload: the `MilestoneEvent` JSON) on each
  accepted milestone.

## What it does not do

- It does not hash anything. The backend hashes; the chaincode only checks that a hash is 64
  lowercase hex characters.
- It does not store amounts or private data (non-essential feature N1).
- It does not choose endorsers. The both-orgs rule is the endorsement policy set at deploy time
  (`network/env.example.sh`, D-05), not code in this package.
- It does not talk HTTP. The gateway (`gateway/`) calls it.

## Transactions

Names equal `ChaincodeFunction` in `backend/s14/contracts.py`. Every argument is a string.
Argument lists are `CHAINCODE_ARGS`; result shapes are `CHAINCODE_RESULT`.

| Transaction | Args | Returns (JSON) | Kind |
|---|---|---|---|
| `CreateRecord` | `sb_hash` | `ShippingBillRecord` | write |
| `RecordMilestone` | one `MilestoneSubmission` as JSON | `MilestoneEvent` | write |
| `GetRecord` | `sb_hash` | `ShippingBillRecord` | read |
| `ListRecords` | none | list of `ShippingBillRecord`, in `sb_hash` order | read |

Rules, all taken from `contracts.py` (`WRITER_ROLE`, `PRECONDITIONS`, `REPEATABLE`,
`REFERENCE_REQUIRED`, `DEFAULT_MSP_ROLES`, `CREATE_RECORD_ROLE`):

- Only `CREATE_RECORD_ROLE` (the AD bank) may call `CreateRecord`. That MSP becomes `bank_msp`.
- The caller's MSP is mapped to a role with `DEFAULT_MSP_ROLES`. An MSP with no role may write
  nothing (ISS-p2-5).
- Bank milestones may be written only by the record's own `bank_msp` (ISS-p2-7).
- `RecordMilestone` check order, first failure wins (ISS-p2-3): `VALIDATION`, `WRONG_ROLE`,
  `WRONG_BANK`, `DUPLICATE_MILESTONE`, `PRECONDITION_FAILED`.
- `RecordMilestone` on a missing record gives `NOT_FOUND`. The submission must match
  `MilestoneSubmission` exactly: unknown fields are rejected (ISS-p2-6), as in Python.
- `ledger_time` is the transaction timestamp as ISO 8601 UTC with `Z` (ISS-p2-2). It comes from
  the proposal, so it is the submitting client's clock when it built the signed proposal. It
  shows when a record was submitted, not when the real-world step happened (U-12; evidence in
  `docs/logs/p2.md`, 2026-10-23 00:42).

## Errors

Errors are thrown as `RuleError`. The message is `"<ErrorCode>: <text>"`, and the peer reports
it as `chaincode response 500, <ErrorCode>: <text>`. The gateway reads the code from there
(D-21). Codes the chaincode raises: `VALIDATION`, `NOT_FOUND`, `ALREADY_EXISTS`, `WRONG_ROLE`,
`WRONG_BANK`, `PRECONDITION_FAILED`, `DUPLICATE_MILESTONE`. The HTTP status for each is
`ERROR_HTTP_STATUS` in `contracts.py`; the gateway applies it, not this package. The other
`ErrorCode` values are produced by the gateway.

Every endorser must build a byte-identical result, so the code never reads the peer's own clock.

## Build, typecheck, test

```bash
cd chaincode
npm ci
npm run typecheck     # tsc --noEmit (src), then tsc -p tsconfig.test.json (src + test + vitest config)
npm test              # vitest run (70 tests on 24 Oct 2026: 2 parity + 26 rules + 42 receiptBook)
npm run build         # tsc -> dist/ (the peer runs dist/index.js via `npm start`)
```

Unit tests never need the network. Do not weaken or skip a spec test to get green; log it as an
issue instead (AGENTS.md section 6).

## Deploy to the Drunix test network

The network and deploy scripts belong to P3. See `network/README.md`.

```bash
bash network/up.sh        # network + channel receiptbook
bash network/deploy.sh    # packages this folder with -ccl typescript and the AND policy
```

- Before the first deploy on any machine, run `docker pull hyperledger/fabric-nodeenv:2.5 &&
  docker tag hyperledger/fabric-nodeenv:2.5 npcioss/fabric-nodeenv:2.5`. Drunix's own node
  runtime image is not published (ISS-p3-8). That upstream's image is a correct substitute is
  [I]; our chaincode ran with it.
- Evidence that TypeScript chaincode builds, installs on both orgs' lite peers, commits under
  `AND('Org1MSP.peer','Org2MSP.peer')` and runs on Drunix: `docs/logs/p2.md`, 2026-10-20 15:55
  (U-07, closed).
- Live calls with the `peer` CLI (create, two milestones, three rejections): `docs/logs/p2.md`,
  2026-10-23 00:42.
- Redeploying on a network that already has `receiptbook` needs a new version and sequence.
  A fresh `network/down.sh` + `network/up.sh` avoids that.

## Known issues

- ISS-p2-9: `peer chaincode invoke --waitForEvent` against the lite peers times out although the
  transaction commits. Query afterwards instead of waiting. See also `network/last-block.sh`.
- ISS-p3-9: after the host sleeps, a Drunix committing peer can panic because its state DB
  died. Check before trusting the network (`network/README.md`).
- The endorsement negative test (one org alone cannot write) was run on Drunix's `basic` sample,
  not yet on `receiptbook` (DEP-p3-3, `docs/logs/p3.md`, 2026-10-22 20:22).
- The live `WRONG_BANK` test needs a second AD bank org (N2). It is covered by unit tests only.
- `ListRecords` is a paged range query over all keys (`LIST_PAGE_SIZE` = 1000), sorted and
  de-duplicated in the chaincode (ISS-p2-10). Drunix's SQL state DB caps an unpaged range scan at
  10 rows (source-verified), and its next-page bookmark looks broken [I], so on Drunix one call
  may return at most 1000 records. Behaviour with many records is untested; we make no claim
  about scale.
