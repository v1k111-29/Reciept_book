## Contract change requests

- CCR-p3-1: contracts do not say which `ChaincodeFunction` is a write (/submit) and which is a read
  (/evaluate). If CreateRecord is sent to /evaluate, the gateway would return `ok=true` with a record
  payload and commit nothing. Proposal: add `CHAINCODE_WRITES = {CREATE_RECORD, RECORD_MILESTONE}` (or a
  route per function); the gateway answers VALIDATION when a function arrives on the wrong route.
  Affects p3 and p4.
- CCR-p3-2: there is no code for "outcome unknown". A submit can time out while waiting for commit status
  after the transaction has been sent with a tx id, and it may still commit. Source: Fabric
  docs/source/write_first_app.rst, "Handle transaction errors" (CommitStatusError carries a
  TransactionID; timeout case). Drunix is assumed to behave the same [I]. Mapping this to
  LEDGER_UNAVAILABLE (503) invites the backend to retry, and a retried CUSTOMS_STATUS_OBSERVED
  (`REPEATABLE`) would be recorded twice. Proposal: (a) failed results carry `tx_id` whenever one was
  assigned (the `GatewayResult` validator already allows it); (b) either add a code such as
  `OUTCOME_UNKNOWN`, or state that the backend never auto-retries a submit that failed with a `tx_id`.
  Affects p3 and p4.
- CCR-p3-3: commit-time validation failures have no `ErrorCode`. One example is two writes to the same
  sb_hash at once, which gives MVCC_READ_CONFLICT. CommitError carries a status code (same Fabric doc
  source). `ENDORSEMENT_FAILED` is described only as "endorsement policy not satisfied". Proposal: say
  that `ENDORSEMENT_FAILED` also covers the ENDORSEMENT_POLICY_FAILURE commit code, and add a retryable
  `CONFLICT` (409) for MVCC conflicts, or else state that they map to INTERNAL. Until the lead decides,
  I will map them to INTERNAL.
- CCR-p3-4 (clarifications, no new types):
  - (a) The `"<ErrorCode>: message"` rule needs a note on how the error arrives. The gateway does not
    receive it at the start of the message. EndorseError puts it in `details[]`, one per peer, as
    `"chaincode response 500, <message>"` (same Fabric doc source). Proposal: the gateway reads the code
    after that prefix in any peer's detail; with an unknown code or no code it answers INTERNAL; when the
    two peers report different codes it answers ENDORSEMENT_FAILED.
  - (b) `tx_id` on /evaluate results: proposal is always null (nothing is committed).
  - (c) `identity` names a role with no configured credentials (e.g. CUSTOMS_VIEWER before N3).
    Proposal: VALIDATION (422).
  - (d) The /health body `{status, contracts_version}` is defined only in a server.ts comment. If the
    backend checks `contracts_version`, it should be in contracts.
